# 50-Role Architecture Review — 2026-09-13

## Scope

This is a structured 50-role review of the merged autonomous coding/control-plane stack plus the `feat/100k-leverage-fabric` and deterministic-transform worker tranche. It is a review framework using 50 independent specialist lenses, not a claim that 50 human reviewers participated.

## Current position

- autonomous coding loop, fenced local workers, repair convergence, branch/PR promotion and guarded 2x throughput are merged to control-plane `main`;
- local compute fabric autonomous coding worker is merged to its `main`;
- leverage-fabric branch adds solution/artifact CAS, semantic graph, transform registry, repair memory, trajectory harvesting, replay, product-family planning, maintenance batching, bottleneck/context/speculation layers and updated documentation;
- deterministic worker branch adds model-free precomputed writes for exact deterministic transforms;
- Patch Fabric / micro-lane design is documented but not yet implemented as a composer/shard authority;
- control-plane `main` currently has no GitHub repository ruleset, so merge protection depends on operator discipline rather than enforced policy;
- approved organization-local runner availability has previously become a validation bottleneck.

## 50 review lenses

### Architecture — roles 1-5
1. **Chief architect:** keep the leverage fabric modular; freeze versioned interfaces between CAS, graph, transforms, scheduler and runtime before further fan-out.
2. **Distributed-systems architect:** Patch Fabric needs a first-class shard/patch-bundle schema and central composer authority; documentation alone is insufficient.
3. **Platform architect:** separate durable authoritative state from disposable acceleration state in storage and recovery code, not only documentation.
4. **Evolution architect:** add ADRs for 100k effective leverage, Patch Fabric and optimization-layer authority boundaries.
5. **Complexity reviewer:** the 100k branch is broad; require capability-level acceptance tests so future refactors cannot silently break compounding paths.

### Reliability — roles 6-10
6. **SRE:** remove single-runner-class validation dependency; support multiple approved org-local runners/capability labels.
7. **Chaos engineer:** add failure tests for worker death during write/verify/publish, composer death mid-apply, cache corruption and control-plane restart during repair.
8. **Recovery engineer:** event replay needs deterministic checkpoints/hash verification and explicit rebuild tests from empty derived state.
9. **Storage engineer:** solution/artifact caches need disk quotas, eviction metrics, corruption detection and atomic persistence.
10. **Availability engineer:** Admin/model/index/cache loss must degrade capabilities independently; no optional component may fail the autonomous loop globally.

### Security/governance — roles 11-15
11. **AppSec:** enforce network-egress policy for coding workers/models so a compromised prompt cannot turn workspace access into arbitrary exfiltration.
12. **Supply-chain security:** generate SBOM/provenance for built artifacts and record toolchain/model/transform versions with accepted evidence.
13. **Secrets engineer:** strengthen trajectory redaction using explicit secret scanners/pattern registry before training export.
14. **Identity engineer:** replace broad long-lived service bearer tokens with scoped/rotatable worker and operator credentials where practical.
15. **Repository-governance reviewer:** protect `main` with rulesets/branch policy requiring accepted local-org validation and no direct pushes for critical repos.

### Scheduling/throughput — roles 16-20
16. **Scheduler engineer:** implement a micro-shard cost model using measured decomposition, transfer, execution, composition and verification time.
17. **Queueing specialist:** reserve verifier/composer capacity before fan-out; shard count must contract before downstream queues saturate.
18. **Fairness reviewer:** micro-lanes must not starve long-running critical-path tasks or low-volume repositories.
19. **Speculation reviewer:** speculative candidates need a portfolio compute budget and expected-value threshold, not only free slots.
20. **Capacity engineer:** weak-host specialization should be explicit: transform/index/test/document shards vs reasoning/browser/device workloads.

### Coding-agent/code-intelligence — roles 21-25
21. **Code-intelligence engineer:** current lightweight source indexing should gain Tree-sitter/SCIP-compatible adapters for precise symbol/reference data.
22. **Compiler/codemod engineer:** deterministic transforms need typed preconditions/postconditions, language/version guards and reversible manifests.
23. **Context engineer:** context bundles need freshness/source-SHA metadata and strict token/size budgets.
24. **Multi-language engineer:** normalize capability contracts across JS/TS, Python, PHP/WordPress, Android/Kotlin and C#/Unity instead of assuming Node-centric verification.
25. **Agent-interface reviewer:** expose structured read/write/search/graph operations so models do not spend reasoning cycles rediscovering repository structure.

### Verification/release — roles 26-30
26. **Verification architect:** distinguish shard checks, composition checks and parent acceptance; targeted success must never imply parent success.
27. **Test reliability engineer:** detect flaky tests and quarantine/investigate them instead of consuming repair loops repeatedly.
28. **Release engineer:** add exact-SHA canary/progressive rollout support for products where deployment topology permits it.
29. **Regression engineer:** add impact-based test selection, but require full-tier verification at policy-defined risk boundaries.
30. **Merge authority reviewer:** create one parent PR for composed shards and persist shard evidence as attachments/ledger records, not PR spam.

### Data/training/model quality — roles 31-35
31. **ML data engineer:** version trajectory schemas and dataset manifests; accepted production outcomes should be reproducible from provenance.
32. **Eval engineer:** enforce train/eval contamination checks continuously, including semantic near-duplicate detection rather than IDs only.
33. **Model-routing engineer:** route by observed acceptance/cost/latency per task class, repository and language; demote regressions automatically.
34. **Learning-systems engineer:** never auto-promote a newly trained model without held-out eval + shadow/canary comparison against the incumbent.
35. **Data-governance reviewer:** support deletion/revocation lineage so a source artifact can be removed from future training sets without corrupting audit history.

### Patch Fabric/composition — roles 36-40
36. **Patch-composition engineer:** implement textual + resource + semantic conflict graphs before enabling broad same-repo sharding.
37. **Version-control specialist:** every shard needs before hashes/base SHA; stale bundles must fail rather than auto-rebase blindly.
38. **Semantic-merge reviewer:** API/schema/invariant changes need dependency ordering even when textual hunks do not overlap.
39. **Performance reviewer:** start with same-pattern fan-out and independent-file shards; postpone arbitrary same-file concurrent editing.
40. **Patch-cache engineer:** content-address patch bundles so repeated portfolio changes can reuse verified shard outputs when source identities match.

### Operations/observability — roles 41-45
41. **Observability engineer:** expose leverage strategy counts, cache hit/miss, shard fan-out, composition conflicts, reasoning avoided and accepted throughput in Admin.
42. **Incident commander:** define one-command pause/drain/reconcile/rollback for autonomous coding and Patch Fabric independently.
43. **Runner-fleet operator:** advertise runner/worker capabilities and health through one shared capacity model; GitHub runner labels must not be the scheduler.
44. **Performance engineer:** measure checkout/worktree/model warmup/test setup overhead; these may dominate 30-second micro-shards.
45. **Cost engineer:** account for compute spent on rejected speculative candidates and failed shards when calculating effective leverage.

### Product/economics/portfolio — roles 46-50
46. **Product-factory lead:** formalize canonical family baselines for SaaS, WordPress, Android and Unity before large fan-out.
47. **Portfolio strategist:** prioritize transformations that apply across dozens/hundreds of products; one-to-one agent work should become a minority path.
48. **Valuation reviewer:** measure maintainability/reuse and reduction in owner intervention, not raw generated LOC, as value creation.
49. **Operations-economics reviewer:** cap infrastructure growth until cache/reuse/sharding utilization proves additional hardware will increase accepted throughput.
50. **Owner-attention reviewer:** Admin should surface only exceptions, bottlenecks, irreversible approvals and confidence drops; routine accepted work should disappear into summaries.

## Consolidated priority backlog

### P0 — before broad autonomous/micro-lane expansion
1. **Repository protection:** enforce branch/ruleset policy on critical `main` branches; direct unvalidated merges must not remain possible.
2. **Patch bundle + composer authority:** implement immutable shard schema, mutation-scope checks, before-hash validation, conflict graph, integration worktree and parent acceptance.
3. **Multi-runner local validation resilience:** at least two approved organization-local runner/worker paths or capability-equivalent failover.
4. **Worker egress/secrets hardening:** bounded network policy and stronger secret-redaction/scanning before data harvest.
5. **Authoritative-vs-derived persistence separation:** prove that caches/indexes/training data can be deleted/rebuilt without losing claims/acceptance truth.

### P1 — largest throughput multipliers
6. Precise AST/symbol indexing adapters (Tree-sitter/SCIP-compatible boundary).
7. Adaptive micro-shard sizing + verifier/composer reservation model.
8. Deterministic transform pre/postcondition/version schema and rollback manifests.
9. Durable content-addressed artifact/build/test cache shared across workers.
10. Repair/solution similarity retrieval with immutable-source safety.
11. Product-family baselines for SaaS, WordPress, Android and Unity.
12. Admin leverage dashboard: reasoning avoided, hit rates, conflicts, accepted throughput and bottlenecks.
13. Automatic training/eval export with semantic contamination checks and model shadow evaluation.

### P2 — scale and polish
14. Impact-based test selection with policy-defined full-test boundaries.
15. Speculative-solution budget optimizer.
16. Flaky-test classification/quarantine.
17. Progressive/canary release adapters where product topology supports them.
18. SBOM/attestation and signed evidence bundles.
19. Learned worker specialization and predicted task duration.
20. Chaos/recovery suite spanning control plane + fabric + composer + caches.

## Recommended next execution order

`P0 repository/authority safety -> Patch Fabric MVP -> runner/failover resilience -> AST/index precision -> adaptive shard scheduler -> shared artifact cache -> product-family baselines -> training/model feedback -> speculative scaling`

This sequence maximizes accepted throughput while keeping coordination, validation debt and security risk below the point where more parallelism becomes negative leverage.
